# Repo Metadata — Protocol

Read this before creating or updating `metadata/INDEX.md`. Otherwise you shouldn't be reading this file at all.

## What this is

`metadata/INDEX.md` is a hand-maintained table giving one row of metadata per device config in this repo: device name, board, domain, purpose, and key components. It exists so a fresh session can answer "what devices exist / what does X do / is there already something for Y" without opening every `*.yaml` file. It is a map, not documentation of behavior — for the real logic, open the file.

Unlike `knowledge-base/components/*.md` (regenerated by `scripts/kb_build.py`), there is no generator script for this file. It is maintained by direct edit, following the rules below.

## Scope

- One row per root-level single-file device config (`*.yaml` in the repo root, excluding `secrets.yaml`).
- One row per package-based device directory (currently `_powmr-inverter-/`, entry point `main.yaml`), with its package files listed in the Notes column rather than given their own row.
- `archive/` is never touched or indexed — those configs are retired (per `CLAUDE.md`).
- `.esphome/`, `build/`, `*.bin`, `*.elf`, `*.map` are never indexed.

## Row schema

```
| File | esphome.name | Platform / Board | Domain | Purpose | Exposes | Consumes | Notes |
```

- **File** — filename relative to repo root.
- **esphome.name** — the `esphome.name` (or `friendly_name` if that's what's distinctive) value, verbatim.
- **Platform / Board** — e.g. `esp8266 / d1_mini`, `esp32 / esp32-c3-devkitm-1`.
- **Domain** — one or two words: room, system, or function area (e.g. `heating`, `garden`, `water`, `security`, `dashboard`). Keep domain words consistent across rows so the table can be scanned/grepped by area.
- **Purpose** — one short sentence, what the device actually does.
- **Exposes** — the ESPHome-generated entity ID (`domain.object_id`) for every named entity this device publishes — IDs only, comma-separated, no source name, no description of what the entity does: `switch.ats_panou, binary_sensor.use_1_acces`. Generate this with `scripts/extract_entity_ids.py` (see "Extracting entity IDs" below) rather than hand-deriving slugs — don't guess the sanitization by eye. Include diagnostic entities (wifi_signal, uptime) too. Entities with no `name:` (internal-only, e.g. a `platform: homeassistant` mirror sensor used only in a lambda) don't get an ID here — they have no HA-facing entity of their own. For package-based entries, a full per-entity listing is not required (see the `_powmr-inverter-` row) — summarize by domain and count, and point at the package file for the exact list.
- **Consumes** — entity IDs (or, for HA service calls with no target entity, the service ID) this device reads from or writes to outside itself, extracted verbatim from the config (not slugified — these are literal `entity_id:` / `service:` values already written in the YAML): `reads: sensor.statie_meteo_luminozitate` / `writes: switch.centrala_lemne_releu_static`. `scripts/extract_entity_ids.py` extracts these too. If the entity's producing file isn't in this repo (e.g. a phone's `notify.mobile_app_*`), leave it as-is — don't invent a source. The routine `time: platform: homeassistant` clock sync present in several configs is boilerplate, not a data dependency — the script already excludes it, do not add it back.
- **Notes** — anything else that affects safety or cross-file reasoning: uses `deep_sleep` (device is usually offline), MQTT instead of/alongside the API, known bugs/TODOs mentioned in the file's own comments, or (for package-based entries) the list of package files. If another device's `Consumes` column references an ID produced by this file, mirror that fact here too (e.g. "switch.releu_centrala_gaz read by bmp280-bucatarie.yaml") — **but only if the literal ID matches this device's own `Exposes` entry exactly**. It sometimes won't: Home Assistant disambiguates colliding entity_ids by prefixing the device name (or a manual rename in HA's entity registry), so a consumer's literal `entity_id:` can differ from what this device would generate by default (see the caveat below). When it differs, note the mismatch instead of asserting they're the same ID — e.g. senzor-vant.yaml's own generated ID for "Luminozitate" is `sensor.luminozitate`, but candel-p.yaml and esp32-monitor.yaml both reference it as `sensor.statie_meteo_luminozitate` (device-prefixed, presumably renamed in HA to avoid a collision with another device's generically-named sensor).

### Caveat: predicted ID vs. real HA entity_id

`Exposes` IDs are ESPHome's own default `object_id` derived purely from the entity's `name:` (lowercase, ASCII-transliterated, non-alnum → `_`) — this is what the user asked for and it's fully reproducible from the YAML alone. It is **not guaranteed** to be the literal entity_id inside a specific Home Assistant instance: HA's entity registry can prefix the device name to avoid a collision with another entity of the same generated ID, and entities can be renamed by hand in the HA UI at any time — neither is visible from this repo. `Consumes` IDs, by contrast, are extracted verbatim from an actual `entity_id:`/`service:` reference already written in someone's config, so they're ground truth for what that device queries/controls, even when they don't match the producing device's predicted `Exposes` ID. Confirmed examples of this mismatch in this repo: `senzor-vant.yaml` ("Luminozitate" → predicted `sensor.luminozitate`, referenced elsewhere as `sensor.statie_meteo_luminozitate`) and `centrala-lemne.yaml` ("Releu Static" → predicted `switch.releu_static`, referenced by candel-p.yaml as `switch.centrala_lemne_releu_static`).

## Extracting entity IDs

Use `scripts/extract_entity_ids.py` whenever you need to (re)populate the `Exposes`/`Consumes` columns — don't hand-slugify names or hand-grep for `entity_id:`, the script already handles substitutions (`${var}`), unicode/diacritic normalization, and homeassistant read/write classification consistently.

```
python3 scripts/extract_entity_ids.py <file.yaml> [<file2.yaml> ...]
python3 scripts/extract_entity_ids.py --ids-only *.yaml   # drop the source-name comments, ID lines only
```

Output is grouped per file into `EXPOSES:` and `CONSUMES:` sections; feed the IDs straight into the row (see caveat above before asserting a producer/consumer match).

Never put credential values, `!secret` contents, or full encryption keys in this file, even though the source YAML has them inline — the file may be shared or the key strings copy-pasted elsewhere by mistake.

## When to update `metadata/INDEX.md`

Update the relevant row in the **same turn** as any change to a device config that affects a column above:

- Renaming `esphome.name`, changing board/platform, or changing what the device actually does → update Purpose/Domain as needed.
- Adding, removing, or renaming any entity's `name:` (sensor, binary_sensor, switch, climate, number, text_sensor, light, button, etc.) → update Exposes.
- Adding/removing a `platform: homeassistant` entity or a `homeassistant.service` call, or changing which HA entity_id it targets → update Consumes (and mirror the link in the producing file's Notes, per the schema above).
- Adding a new `*.yaml` device config at the repo root → add a row.
- Deleting a device config, or moving one into `archive/` → remove its row.
- Adding/removing a package file under a package-based device directory → update that entry's Notes list.

Small edits unrelated to the columns above (tweaking a `filters:` calibration value, adjusting a threshold, fixing a typo in an entity name) do not require an INDEX update — don't touch this file just because you touched the device's YAML.

If you can't tell from the task whether a change alters the device's purpose/domain enough to warrant a row update, ask the operator one specific question rather than guessing at a new Purpose line.

## How to update

1. Make the YAML change first, validate it (per `CLAUDE.md` workflow).
2. Edit only the affected row(s) in `metadata/INDEX.md` — do not reformat or reflow the table, do not touch unrelated rows.
3. Mention the INDEX update in your report alongside the YAML change; it does not need separate confirmation.

## Bootstrapping / full rebuilds

A full rebuild (re-deriving every row from scratch) is only done on explicit request — e.g. "rebuild metadata/INDEX.md" or after a large batch of untracked config changes. Routine work only ever touches the rows for files actually being edited in that session.
